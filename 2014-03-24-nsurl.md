There is a simple beauty to what we might call "one-dimensional data types":
numbers or strings formatted to contain multiple values,
retrievable through a mathematical operator or parsing routine.
Like how the hexadecimal color <code style="color: #EE8262;">#EE8262</code>
can have [red, green, and blue components](https://en.wikipedia.org/wiki/Web_colors)
extracted by masking and shifting its bits,
or how [regular expressions](https://en.wikipedia.org/wiki/Regular_expression)
can match and capture complex patterns in just a few characters.

Of all the one-dimensional data types out there,
[URIs](https://en.wikipedia.org/wiki/URI_scheme) reign supreme.
Here, in a single, human-parsable string,
is every conceivable piece of information necessary
to encode the location of any piece of information
that has, does, and will ever exist on a computer.

In its most basic form,
as defined by [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986),
a URI is comprised of a scheme name and a hierarchical part,
with an optional query and fragment:

```
URI = scheme ":" hier-part [ "?" query ] [ "#" fragment ]
```

Many protocols, including HTTP,
specify a regular structure for information like
the username, password, host, port, and path in the hierarchical part:

```
https://johnny:p4ssw0rd@www.example.com:8080/search/results?q=swift&sort=new#top
└─┬─┘   └─┬──┘ └──┬───┘ └──────┬──────┘ └┬─┘└──────┬──────┘ └──────┬───────┘ └┬┘
  │       │       │            │         │         │               │          │
scheme    │   password         │       port        │             query        │
          │                    │                   │                          │
        user                 host                path                     fragment
```

A solid grasp of network programming is rooted in
an unshakeable familiarity with URL components.
As a software developer,
this means having a command over the URI functionality
in your programming language's standard library.

> If a programming language does not have a URI module in its standard library,
> run, don't walk, to a real language that does.

---

When this article was first written,
URLs in Foundation meant `NSURL` and `NSURLComponents`.
Swift 3 brought the `URL` and `URLComponents` value types,
which bridge to those classes,
and over the years they've picked up enough Swift-only API
that there's little reason to reach for the `NS` versions anymore.

## URLComponents

`URLComponents` can best be described by
what it could have been named instead: `MutableURL`.
It takes a URL apart into the pieces in the diagram above,
with a property for each one:

```swift
let components = URLComponents(
    string: "https://johnny:p4ssw0rd@www.example.com:8080/search/results?q=swift&sort=new#top"
)!

components.scheme   // "https"
components.user     // "johnny"
components.password // "p4ssw0rd"
components.host     // "www.example.com"
components.port     // 8080
components.path     // "/search/results"
components.query    // "q=swift&sort=new"
components.fragment // "top"
```

It also works in the other direction.
Start with an empty value,
set whatever properties you need,
and ask for the `url` (or its `string`) at the end:

```swift
var components = URLComponents()
components.scheme = "https"
components.host = "nshipster.com"
components.path = "/search"
components.queryItems = [URLQueryItem(name: "q", value: "url components")]

components.url
// https://nshipster.com/search?q=url%20components
```

These properties take and return plain, decoded strings;
`URLComponents` adds and removes [percent-encoding](https://en.wikipedia.org/wiki/Percent-encoding) as needed.
If you already have encoded values,
use the corresponding `percentEncodedUser`, `percentEncodedPassword`,
`percentEncodedPath`, `percentEncodedQuery`, and `percentEncodedFragment` properties,
or `encodedHost`,
which iOS 16 and macOS 13 added as the successor to `percentEncodedHost`.

A few things will stop your program cold.
Setting a scheme with invalid characters,
a negative port,
or one of the `percentEncoded` properties with an incorrectly encoded string
is a `fatalError`.
And `url` returns `nil` if the components have a host
and a path that doesn't start with a `/`,
so `components.path = "search"` would have gotten us `nil` above.

> Although a username and password _can_ be stored in a URL,
> keep credentials in the keychain,
> and send them in a header rather than in the URL itself.

## Parsing URLs

For most of its history,
`URL(string:)` was famously strict.
Pass it a string with a space or a non-ASCII character,
and you got back `nil`.

That changed in iOS 17 and macOS 14.
For apps linked on or after those SDKs,
`URL` parses strings according to RFC 3986,
the same way `URLComponents` always has,
instead of the obsolete RFC 1738 and RFC 1808 rules that `NSURL` was built on.
`URL(string:)` now percent-encodes invalid characters
(and IDNA-encodes internationalized host names)
to make a valid URL out of whatever you give it:

```swift
URL(string: "https://example.com/hello world")
// Linked before iOS 17: nil
// Linked on or after iOS 17: https://example.com/hello%20world
```

It still returns `nil` for the empty string,
or for a string that remains invalid after encoding.
If you're validating input and want the old strictness,
use the new `init(string:encodingInvalidCharacters:)` initializer
and pass `false`:

```swift
URL(string: "https://example.com/hello world",
    encodingInvalidCharacters: false)
// nil
```

`URLComponents` gained a matching `init(string:encodingInvalidCharacters:)`
in the same release.

### Relative URLs

`URL(string:relativeTo:)` resolves a string against a base URL,
and the way it treats a leading `/` continues to be a source of confusion.
For reference, here's how it works:

```swift
let baseURL = URL(string: "https://example.com/v1/")!

URL(string: "foo", relativeTo: baseURL)!.absoluteString
// "https://example.com/v1/foo"

URL(string: "foo?bar=baz", relativeTo: baseURL)!.absoluteString
// "https://example.com/v1/foo?bar=baz"

URL(string: "/foo", relativeTo: baseURL)!.absoluteString
// "https://example.com/foo"

URL(string: "https://example.org/", relativeTo: baseURL)!.absoluteString
// "https://example.org/"
```

The resulting `URL` keeps track of its `baseURL` and `relativeString`,
which is why you'll want `absoluteString` (or `absoluteURL`)
when you need the whole thing.

## Query Items

The `queryItems` property of `URLComponents`
gives you the key-value pairs in a query string
as an array of `URLQueryItem` values,
in the order they appear.
Names aren't guaranteed to be unique,
and a value is `nil` when its pair has no `=`.

Setting `queryItems` is the right way to put arbitrary text into a query,
because `URLComponents` encodes any `&` or `=` in each name and value
so that they can't be mistaken for delimiters.
It doesn't do the same for `+`, though:

```swift
var components = URLComponents(string: "https://example.com/search")!
components.queryItems = [
    URLQueryItem(name: "q", value: "swift & objective-c"),
    URLQueryItem(name: "lang", value: "c++")
]

components.percentEncodedQuery
// "q=swift%20%26%20objective-c&lang=c++"
```

RFC 3986 allows `+` in a query,
and `URLComponents` reads it back as `+`.
But many servers decode queries using the rules for HTML form submissions,
where `+` means a space.
To them, `lang` is "c" followed by two spaces.

If that's a concern,
percent-encode the names and values yourself,
escaping `+` as `%2B`,
and set `percentEncodedQueryItems`
(available since iOS 11 and macOS 10.13):

```swift
var allowed = CharacterSet.urlQueryAllowed
allowed.remove(charactersIn: "&=+")

let q = "swift & objective-c".addingPercentEncoding(withAllowedCharacters: allowed)
let lang = "c++".addingPercentEncoding(withAllowedCharacters: allowed)

components.percentEncodedQueryItems = [
    URLQueryItem(name: "q", value: q),
    URLQueryItem(name: "lang", value: lang)
]

components.percentEncodedQuery
// "q=swift%20%26%20objective-c&lang=c%2B%2B"
```

`percentEncodedQueryItems` trusts that you've done your job:
an item with invalid percent-encoding,
or a name containing `&` or `=`,
is a `fatalError`.

## Building URLs

iOS 16 and macOS 13 gave `URL` a set of methods
that cover what most of us used `URLComponents` for in the first place.
`appending(queryItems:)` adds query items
(encoding them the same way as `queryItems`),
and `appending(path:)` adds to the path:

```swift
baseURL.appending(path: "search")
       .appending(queryItems: [URLQueryItem(name: "q", value: "swift")])
// https://example.com/v1/search?q=swift
```

`appending(path:)` doesn't follow the rules for relative URLs.
A leading `/` is simply joined to the existing path,
and characters like `?` that aren't allowed in a path
are percent-encoded rather than interpreted:

```swift
baseURL.appending(path: "/foo")
// https://example.com/v1/foo

baseURL.appending(path: "search?q=swift")
// https://example.com/v1/search%3Fq=swift
```

`appending(path:)` leaves `/` alone,
which is what you want for a path, but not for a single name.
Use `appending(component:)` when the string is one path component,
such as a user-supplied identifier,
and `/` should be encoded too:

```swift
let artists = URL(string: "https://example.com/artists/")!

artists.appending(path: "AC/DC")
// https://example.com/artists/AC/DC

artists.appending(component: "AC/DC")
// https://example.com/artists/AC%2FDC
```

(For file URLs, `appending(component:)` doesn't encode `/`.)

## File URLs

URLs are also the preferred way to refer to files,
and a file URL is a different beast from a web URL.
Make one with `URL(filePath:)`,
or start from one of the static properties for common locations,
like `URL.documentsDirectory`, `URL.cachesDirectory`, or `URL.temporaryDirectory`
(all available since iOS 16 and macOS 13):

```swift
let draft = URL.documentsDirectory.appending(path: "Drafts/notes.md")
```

`URL(string:)` is the wrong tool for a file system path.
`URL(string: "/Users/mattt/notes.md")` succeeds,
but what you get is a relative URL with no scheme,
and its `isFileURL` is `false`.

`URL(filePath:)` and the `appending` methods also take a `directoryHint`.
The default, `.inferFromPath`, treats a path with a trailing `/` as a directory;
pass `.checkFileSystem` to have Foundation look on disk instead.

When you need to hand a path to something that wants a `String`,
reach for `path(percentEncoded:)`,
which replaces the `path` property that's now slated for deprecation.
Take note of its default:

```swift
let url = URL(filePath: "/Users/mattt/My Notes.txt")

url.absoluteString              // "file:///Users/mattt/My%20Notes.txt"
url.path()                      // "/Users/mattt/My%20Notes.txt"
url.path(percentEncoded: false) // "/Users/mattt/My Notes.txt"
```

Calling `path()` with no arguments gives you the percent-encoded form,
which is correct for a URL and wrong for the file system.
(`host`, `query`, `fragment`, `user`, and `password`
have the same kind of replacement.)

## Percent-Encoding

Speaking of percent-encoding...

When you can,
let `URLComponents` or the `appending` methods do the encoding for you.
When you can't,
`addingPercentEncoding(withAllowedCharacters:)`
replaces every character not in the given set with its percent-encoded form,
and `removingPercentEncoding` reverses the process.
`CharacterSet` provides a set for each component that allows percent-encoding:

- `urlUserAllowed`
- `urlPasswordAllowed`
- `urlHostAllowed`
- `urlPathAllowed`
- `urlQueryAllowed`
- `urlFragmentAllowed`

These sets are easy to misuse,
because each one describes what's allowed in an entire component,
not in a single piece of one.

{% warning do %}

Don't use `urlQueryAllowed` to encode the names or values in a query.
It leaves `&`, `=`, `+`, and `?` unescaped,
because they're allowed in a query string,
but inside a value, `&` and `=` are read as delimiters
and `+` is often decoded as a space.
Set the `queryItems` property of `URLComponents` instead,
which escapes any `&` and `=` in each name and value.
If your server decodes `+` as a space,
encode with a set that excludes `+` and set `percentEncodedQueryItems`,
as shown above.

{% endwarning %}

The same goes for `urlPathAllowed`,
which leaves `/` alone,
so a name like "AC/DC" becomes two path segments.

None of these sets include `%`,
so encoding a string that's already encoded
encodes it a second time.
Going the other way,
`removingPercentEncoding` returns `nil`
if it finds a malformed escape sequence, such as a lone `%`.

```swift
"AC/DC".addingPercentEncoding(withAllowedCharacters: .urlPathAllowed)
// "AC/DC"

"caf%C3%A9".addingPercentEncoding(withAllowedCharacters: .urlQueryAllowed)
// "caf%25C3%25A9"

"caf%C3%A9".removingPercentEncoding
// "café"

"100%".removingPercentEncoding
// nil
```

Forget jet packs and flying cars —
my idea of an exciting future is one where everything has a URL,
is encoded in Markdown, and stored in Git.
If your mind isn't blown by the implications of
a _universal_ resource locator,
then I would invite you to reconsider.

Like [hypertext](https://en.wikipedia.org/wiki/Hypertext),
universal identification is a philosophical concept
that both pre-dates and transcends computers.
Together, they form the fabric of our information age:
a framework for encoding our collective understanding of the universe
as a network of individual facts.

Quite lofty implications for a technology
used most often to exchange pictures of cats.
