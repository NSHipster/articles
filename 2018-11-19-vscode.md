[Visual Studio Code (VSCode)](https://code.visualstudio.com)
is a cross-platform text and source code editor from Microsoft.
It's one of the most popular open source projects around,
with regular updates from hundreds of contributors.
VSCode was among the first tools to support
[Language Server Protocol (LSP)](https://microsoft.github.io/language-server-protocol/),
which has played a large part in providing a great developer experience
in a variety of languages and technologies.

When we first wrote about Swift in VSCode,
getting it working meant installing Node and npm,
cloning the sourcekit-lsp repository,
building a `.vsix` package by hand,
and pasting the output of `xcrun --find` into a settings field
when the language server inevitably failed to start.
It was a fun afternoon,
provided your idea of fun involves `npm run createDevPackage`.

That extension is long gone.
In its place is the official
[Swift extension for VS Code](https://marketplace.visualstudio.com/items?itemName=swiftlang.swift-vscode),
maintained by the Swift project
[on GitHub](https://github.com/swiftlang/vscode-swift)
and installable in a single click.

This week,
we'll walk through setting up Swift development in VSCode
and take a tour of what you get once it's running.
If you haven't tried writing Swift outside Xcode,
or are already a VSCode user and new to the language entirely,
this article will tell you everything you need to know.

* * *

## A Brief Word on Language Servers

Before LSP,
every editor that wanted to support a language
had to implement code completion, diagnostics, and navigation for it.
_M_ editors and _N_ languages meant _M × N_ integrations,
most of them half-finished.

Language Server Protocol turns that into _M + N_.
A language provides one server that understands its code;
an editor provides one client that speaks the protocol.
For Swift, that server is
[SourceKit-LSP](https://github.com/swiftlang/sourcekit-lsp),
which ships with every Swift toolchain and with Xcode.
(We covered the protocol in more depth
in [our article on Language Server Protocol](/language-server-protocol/).)

The Swift extension for VSCode is,
at its core,
an LSP client for SourceKit-LSP,
plus Swift-specific tooling for tasks, tests, debugging, and packages.

## Step 1: Install Swift

The Swift project recommends installing toolchains with
[swiftly](https://github.com/swiftlang/swiftly),
a toolchain manager in the spirit of `rustup` or `nvm`.
On macOS,
[swift.org](https://www.swift.org/install/macos/)
gives the following command,
which installs swiftly to your home directory
and fetches the latest stable toolchain:

```terminal
$ curl -O https://download.swift.org/swiftly/darwin/swiftly.pkg && \
  installer -pkg swiftly.pkg -target CurrentUserHomeDirectory && \
  ~/.swiftly/bin/swiftly init --quiet-shell-followup && \
  . "${SWIFTLY_HOME_DIR:-$HOME/.swiftly}/env.sh" && \
  hash -r
$ swift --version
```

The [Linux instructions](https://www.swift.org/install/linux/)
download a tarball instead of a package,
but work the same way.
Later, `swiftly install latest` gets you the newest release,
and `swiftly use` inside a project
can write a `.swift-version` file
so that everyone on your team builds with the same toolchain.
The extension respects that file, too.

{% info do %}

If you already have Xcode installed,
you already have a Swift toolchain,
and the extension will find whichever Xcode `xcode-select` points to.
swiftly is still worth a look if you want a newer toolchain
than the one bundled with Xcode,
or if you also work on Linux.

{% endinfo %}

## Step 2: Install VSCode and the Swift Extension

[Download Visual Studio Code](https://code.visualstudio.com/Download)
and install it.
Then open the Extensions view,
search for "Swift",
and install the one published by **swiftlang**.
Or, from the command line:

```terminal
$ code --install-extension swiftlang.swift-vscode
```

That's it.
No Node, no npm, no `.vsix` files.
The extension pulls in its one dependency,
the [LLDB DAP](https://marketplace.visualstudio.com/items?itemName=llvm-vs-code-extensions.lldb-dap)
extension from the LLVM project,
automatically.
If you use an editor like Cursor or VSCodium
that gets its extensions from [Open VSX](https://open-vsx.org),
you'll find both published there under the same identifiers.

{% warning do %}

The extension looks for `swift` on your `PATH`.
If you install a toolchain while VSCode is open,
quit VSCode entirely and reopen it
so the extension picks up the change.
If you have several toolchains installed,
run **Swift: Select Toolchain...** from the Command Palette
(<kbd>⇧</kbd><kbd>⌘</kbd><kbd>P</kbd>)
to choose between them.

{% endwarning %}

Now open a folder containing a `Package.swift` file,
or run **Swift: Create New Project...**
to generate one from the same templates as `swift package init`.

## What You Get

### Language Features

Once the extension finds a package,
it starts SourceKit-LSP,
and the usual VSCode affordances start working for Swift:
code completion,
Go to Definition (<kbd>F12</kbd>),
Find All References,
Rename Symbol (<kbd>F2</kbd>),
and errors and warnings annotated inline as you type,
with fix-its offered as quick fixes.

Press <kbd>⌘</kbd><kbd>.</kbd>
to see the
[refactoring actions](https://github.com/swiftlang/sourcekit-lsp/blob/main/Documentation/Refactoring%20Actions.md)
available where your cursor is:
expanding a macro,
extracting a method,
generating a memberwise initializer,
converting a completion handler–based function to `async`.
In `Package.swift`,
code actions can even add targets and products to your manifest.

Starting with Swift 6.1,
SourceKit-LSP indexes your project in the background,
so cross-module features work without building first.
(On older toolchains,
run `swift build` at least once,
and again after adding a dependency.)

### Building and Running

For any package,
the extension generates tasks for you:
**Build All**,
**Clean Build Folder**,
and **Build Debug** and **Build Release** variants for each executable.
Run them with **Terminal > Run Build Task...**
(<kbd>⇧</kbd><kbd>⌘</kbd><kbd>B</kbd>).
When you open a file that belongs to an executable target,
Run and Debug buttons appear in the editor's title bar.

### Testing

The extension discovers both
[Swift Testing](https://github.com/swiftlang/swift-testing)
and XCTest tests in your package
and lists them in VSCode's
[Test Explorer](https://code.visualstudio.com/docs/debugtest/testing).
Given a `greet(_:)` function in a `Greeter` module,
a test for it looks like this:

```swift
import Testing
@testable import Greeter

@Test func greeting() {
    #expect(greet("Mattt") == "Hello, Mattt!")
}
```

Run and debug buttons appear inline above each test and suite.
You can also run tests with code coverage,
which marks each line of your source
according to whether your tests reached it.
For flaky tests,
right-click and choose **Run Until Failure...**.

### Debugging

With Swift 6.0 or later,
the extension debugs with `lldb-dap`,
the Debug Adapter Protocol server that ships with LLDB
in the Swift toolchain.
(Older toolchains use the third-party
[CodeLLDB](https://marketplace.visualstudio.com/items?itemName=vadimcn.vscode-lldb)
extension instead.)

The extension generates a launch configuration for each executable,
so you can set a breakpoint, press <kbd>F5</kbd>,
and start inspecting variables.
To pass arguments or environment variables,
customize the configuration in `.vscode/launch.json`.
Naming a `target` and `configuration`
is more portable than hard-coding the path to the built executable:

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "swift",
      "request": "launch",
      "name": "Debug greet",
      "target": "greet",
      "configuration": "debug",
      "args": ["--name", "Mattt"]
    }
  ]
}
```

### Managing Packages

The **Swift Project** panel in the Explorer sidebar
shows your package's targets, tasks, and dependencies,
with buttons to resolve, update, or reset them.
Right-click a dependency and choose **Use Local Version**
to point it at a checkout on your machine
(the same as `swift package edit --path`),
which is handy when the bug you're chasing
lives on the other side of an `import`.

## What About Apps?

Most of what we've described works with projects
that build with Swift Package Manager.
SourceKit-LSP also understands projects
that produce a `compile_commands.json` file (such as CMake projects)
or provide a `buildServer.json` file for the Build Server Protocol.
Support for Xcode projects is,
in the extension's own words, "limited".

So if you're making an app for iPhone, iPad, Mac, or Apple Vision Pro,
you still need Xcode.
VSCode can't build and sign an app bundle,
run it in Simulator,
or render SwiftUI previews.

There is some middle ground.
On macOS with Swift 6.1 or later,
the **Swift: Select Target Platform...** command
points SourceKit-LSP at the iOS, tvOS, watchOS, or visionOS SDK
from your Xcode installation,
though the extension warns that compiling against those SDKs
"will have undefined results".
Third-party tools like
[xcode-build-server](https://github.com/SolaWing/xcode-build-server)
generate a `buildServer.json` from Xcode's build logs,
so SourceKit-LSP can make sense of an Xcode project.
Plenty of developers edit in VSCode
and switch to Xcode to build and run.

Where VSCode shines is everywhere else:
command-line tools, server-side Swift, libraries,
and anything that runs on Linux or Windows.

* * *

When we last updated this article in 2020,
GitHub had just announced
[Codespaces](https://github.com/features/codespaces),
and we predicted that we'd soon be able to edit Swift code ---
syntax highlighting, autocompletion, and all ---
directly from the browser.
That future arrived:
the Swift extension works in
[Dev Containers](https://code.visualstudio.com/docs/devcontainers/containers)
and Codespaces,
backed by the same SourceKit-LSP that powers Xcode.

What we didn't predict was how unremarkable it would become.
Setting up Swift in VSCode is now about as exciting as
setting up any other language,
and that's exactly the point of
[Language Server Protocol](/language-server-protocol/).
